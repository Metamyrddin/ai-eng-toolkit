## How to read these results (hand-written)

* **KV cache.** The cached and uncached greedy outputs are token-identical and the memory formula matches the bytes actually held — the two correctness claims. The speed-up grows with context length (the "per-step cost" table): uncached cost grows with the prefix, cached cost grows only slowly. The single 128-token timing at the top is one run; trust the median sweep.
* **Static batching (HF).** Aggregate decode throughput rises with batch size while per-request speed falls — the classic throughput/latency trade-off. TTFT grows with batch size because the whole padded batch is prefilled together.
* **Quantization (GGUF).** File size shrinks monotonically with bits. **Perplexity** rises as bits fall (read the last column against the HF fp32 reference) — and on this tiny 0.5 B model q2_k is clearly worse than q4_k_m and above. **Decode speed** rises as files get smaller (decode is memory-bandwidth-bound), but prefill speed does *not* follow bits (it is compute-bound and k-quants need extra dequantisation work), so the lowest-bit file is not the fastest at prefill. A residual gap between fp16 GGUF perplexity and the HF fp32 reference remains and we did not find its cause (fp16 rounding and slightly different kernels are plausible but untested). Perplexity uses only 2,044 tokens, so small differences between neighbouring rows (e.g. q5_k_m vs q8_0) may be noise — we did not compute an interval.
* **Python binding vs upstream binary.** `llama-bench` from the upstream release reaches considerably higher prefill tok/s than the llama-cpp-python wheel measured in our table for the same quant — they bundle different llama.cpp builds/CPU kernels. **Do not compare absolute numbers across the two tools**; compare rows within one tool. `llama-bench`'s ± shows large run-to-run variation on this shared VM.
* **RTN-from-scratch quantization (SmolLM2-135M).** 8-bit is nearly lossless; 4-bit per-row is clearly degraded and *group-wise scales help a lot* (smaller groups = better quality but more bits per weight); ≤3-bit round-to-nearest collapses (perplexity in the thousands and up). This is exactly why calibration-based methods (GPTQ, AWQ) exist. Simulated quantization: no memory or speed is gained here.
* **Speculative decoding.** Our implementation is exact in greedy mode (output identical to the target's greedy) in all rows. Acceptance falls as γ grows while *tokens per target call* rises — but fewer target calls ≠ faster: with Hugging Face's `assistant_model` on this CPU the assisted run was **slower** than baseline (ratio < 1), because a 135 M draft is not cheap relative to a 360 M target (only ~2.7× fewer parameters) and CPU overheads dominate. Speculative decoding pays off when the draft is ≥ 10× cheaper and the target is bandwidth-bound — typical of large GPU models, not measured here.
* **Batching simulation** (a simulation: assumed step cost model). At low load the throughput is arrival-limited so both schedulers match, but continuous batching cuts mean latency; at overload it also raises throughput. The real-server measurements below confirm the direction.
* **Real server (llama-server).** With 1 slot, extra concurrent clients just queue: TTFT explodes while throughput stays flat. With 4 slots, throughput rises with concurrency and TTFT stays low. The five trials per cell show the noise (throughput range column).
* **llama-cpp-python's own server** (when the check script is run): at 1 client it works (its throughput is lower than upstream `llama-server`'s), but at 4 concurrent clients most requests returned no tokens (see the failed/empty column) — `bench_serving.py` counts them as failures instead of hiding them, and their tokens are excluded from the throughput figure. We did not investigate the root cause (possibly a server-side concurrency/streaming bug or our request settings); we only report the observation with this version (llama-cpp-python 0.3.36).
