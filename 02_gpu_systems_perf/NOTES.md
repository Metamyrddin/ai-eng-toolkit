## How to read these results (hand-written)

* **Profiler.** On CPU, matrix multiplies dominate the time of a training step (first row). The long tail of small elementwise operators (`mul`, `add`, `fill_`, `silu_backward`) is what a compiler like Inductor tries to fuse. The Chrome trace JSON in `results/` shows the per-operator timeline.
* **torch.compile (CPU).** The valid comparison is the **1-thread** table: compiled and eager steps differ by only ~5 % (single run, median of 20 steps; no variance estimate, so read it as "no meaningful change") (compilation takes 10+ s on first call) — no meaningful gain on this small block, whose time is dominated by matmuls that are not fused anyway. Outputs match eager to ~1e-6. The **8-thread** row is *not valid evidence about Inductor*: this machine has no system C++ compiler, so we compile with an improvised toolchain (`zig c++` plus headers and an OpenMP runtime from PyPI wheels, see `tools/env_inductor_cpu_nocompiler.sh`), and with several threads the compiled kernels end up ~40× slower than eager — a symptom of two different OpenMP runtimes in one process, which we did not fully diagnose. On a normal machine with `g++` (or MSVC) and a GPU, expect different and usually more favourable behaviour; run `compile_bench.py` there.
* **Attention.** Naive, tiled online-softmax and PyTorch SDPA agree to ~1e-6 with a float64 reference — the tiled algorithm is *exact*. The memory table is the point: at sequence length 4096 the naive implementation materialises the full score matrix (about 1 GB extra memory) while the tiled and fused versions need only tens of MB (O(N) instead of O(N²)). In *time*, our pure-PyTorch tiled loop is slower than naive on CPU — expected: FlashAttention's speed comes from keeping tiles in on-chip GPU memory in one fused kernel, which this code does not do. PyTorch's SDPA is far faster than both.
* **SDPA backends on CPU:** only the `MATH` and `FLASH_ATTENTION` (CPU implementation) backends are available; the CUDA-only efficient/cuDNN backends report unavailable with the actual error text.
* **Triton interpreter:** kernels agree with PyTorch within float32 rounding. This validates *logic*; it says nothing about GPU speed.
