## How to read these results (hand-written)

* **SFT + LoRA works on the toy task.** The base 135 M model essentially never answers in the required format (it continues the text), so "before" accuracy is ~3 %; after a short LoRA SFT it answers correctly on over half of 200 *held-out* problems. Trainable parameters are 3.5 % of the total, and merging the adapter into the base weights changes the logits by ~1e-4 (numerical noise): merged and adapter models are equivalent.
* **Rejection-sampling data (best-of-n with a verifier):** the 360 M base model, prompted with 3 few-shot examples, passes the verifier for most samples (`sample_yield`), so the filter is cheap here. Training the 135 M model on the verified answers gives lower accuracy than the template-SFT run — but it saw about half as many training steps (the run used ~1 k examples vs 2 k), so **the comparison is not controlled** and we draw no conclusion about the methods. Its value here is demonstrating the pipeline and the yield measurement. The kept completions are the canonical formatted answer for each verified prompt.
* **DPO did not improve accuracy** (0.565 → 0.50; Δ = −0.065 on 200 problems, within noise of ±0.07 but certainly not an improvement). The training log shows the DPO loss falling and *reward accuracy on the training batches* rising to 0.8–0.95, while `rewards/chosen` drifts negative — the policy learned to separate chosen from rejected mostly by pushing the *rejected* log-probability down, not the chosen one up. This "likelihood displacement" failure mode is documented in the literature (e.g. Pal et al. 2024, *Smaug*, [arXiv:2402.13228](https://arxiv.org/abs/2402.13228)); we did not test whether it is the cause here, and we did not tune β / lr / epochs to make the number look better. Treat this as a negative, honest result.
* **Reward model:** trained from the base model for 60 steps, or from the SFT model for 150 steps, it does **not** beat chance on held-out arithmetic pairs (difference between chosen and rejected is a ±1…±10 error in the answer — you must actually compute the sum to tell). The sanity row proves the code is able to learn: when the rejected answer is a non-number word, held-out pairwise accuracy goes to 1.0 in 40 steps. So the sketch is mechanically correct, and the arithmetic preference task is simply too hard for this budget.
* **Real-text smoke tests** (Capybara SFT, UltraFeedback DPO) confirm that the same code runs on chat-format datasets with a chat-template model (the DPO run has only a handful of optimizer steps and a single logged step: it shows no learning, only that the pipeline runs). No quality claims.
